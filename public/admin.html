This panel needs an admin session. Before, anyone who could reach the port saw every number. Now /status requires a session with the admin role, and the mint socket requires a session at all. Paste the admin key the hub printed at startup (or the one you set with GLM_KEYS=partner:…,admin:…). A superadmin key works here too, and is the only one that can create people — the box tries admin first, then superadmin.

A session is required to read this panel.

This is the operator view. It never runs in a partner's browser. Partner pages only ever see the minter screen, never these numbers. Sign-in: login.html — user, partner and admin roles; partner and admin need that role's key. The hub is server/hub.mjs; the panels below fill with real numbers once it is running (npm run hub), and honestly show placeholders when it is not.

Without GLM_UPSTREAM set, chat answers 501 rather than guessing where to send it. With it set, the hub forwards there (the model id still picks the path, so cn/… keeps its own endpoint), signs each request, and attaches one minted param from the pool as captcha_verify_param. A 401/403/429 puts the entry back instead of burning it; an x-glm-pool: empty response means the request went out with no param. One caller may hold 4 requests at once (GLM_CHAT_CONCURRENCY); the next one gets 429 with a retry-after, then waits GLM_CHAT_COOLDOWN_MS (5s) before trying again. Every chat is minted its own chat_id and answered with x-glm-chat, x-glm-caller and x-glm-caller-kind. Hand the chat_id back to continue that conversation — the hub replays the turns it relayed, so the next request can be one new message — but only the caller that minted it may continue it (anyone else gets the same 404 as an id that never existed). The tag — never the name — is what travels upstream.

The registry comes from GLM_PEOPLE (name=role:key, comma-separated) plus people created here by a superadmin, plus one superadmin seeded at startup from GLM_SUPERADMIN (or a key generated and printed once). A person signs in with their own key and their name then rides on their sessions, mint sockets and donations. Revoke drops the key, the live sessions and the open sockets on the next request; Rotate issues a new key and kills the old one. A key that came from the environment cannot be revoked here — remove it there. Keys are shown only in the moment a new one is created, and only a scrypt hash of each is kept — in memory, and in GLM_STATE_FILE when one is set.

Routed: /v1/chat/completions and the upstream-key probe. Never routed: POST /captcha/verify, the donation exchange, and every local route on this hub.
Routes are the hub's environment, not this page: GLM_EGRESS_ROUTES=host:port[,host:port…] plus GLM_EGRESS_MODE=direct|proxy|tor. A 127.0.0.1 entry means a proxy on the machine running the hub — not on the laptop you are reading this from. A route that fails a handshake is held dead for GLM_EGRESS_DEAD_MS and retried after, while a chat call falls back to direct and labels itself direct-fallback.

Health is what the gate could prove, nothing more. ok: one bounded probe (5 s) got a 2xx from the upstream, so it accepted the token. unverified: not yet proven — either no upstream is configured to probe, or the probe answered something that says nothing about the token; it is never a claim that the token works. dead: the upstream throttled it (429), so it is skipped for 10 minutes. refused: the upstream rejected it (401/403) — a refused token is never stored as a row, so that counter stays 0 and the gate's answer appears in the notice above.
A token is memory only. The hub holds it, spends it on anyone's chat call in place of GLM_UPSTREAM_KEY, and never writes it to the state file, the log or any response: GET /upstream/keys lists metadata, never the value, and POST /upstream/keys/revoke drops a row from memory at once. The form's answer above is the gate's own output, quoted — shape, claims, duplicate and probe, in the order it ran them.

Each row is one donated token or session, shown by its SHA-256 fingerprint — the value itself is never stored or displayed. valid/invalid come from a real Aliyun captcha exchange (POST /captcha/verify with {fp, value} or {param}); unverified means not proven. Verification is admin-only. Each captcha-shaped donation is one outbound exchange, so one caller may have 4 verifying at once (GLM_DONATE_CONCURRENCY); the next gets 429 + retry-after before it is recorded or sent. Donations are verified, never replayed upstream, so volume here is not chat capacity.

The hub exchanges a minted captchaVerifyParam with Aliyun's public verify API — the same scene the minter page drives. Nothing is invented: when the network is unreachable the status is unverified with the reason, never a fabricated valid. The three reference projects instead port the widget's device-data generator in-process; this hub asks the real endpoint, so a "valid" here is what Aliyun actually answered.

Not done yet — and what would finish each one

GapStateWhat it needs — and who already solved it
Upstream / real chat replies forwarding + signing proven A local stub proves the whole call: GLM_UPSTREAM really redirects the destination (the source in the model id still picks the path), GLM_UPSTREAM_KEY rides as a bearer credential, x-signature is a real HMAC over the flattened prompt, the suffix features arrive in the reference projects' features shape, and one pool entry rides each call (check-chat.mjs). What is still unproven: a successful call to the real chat.z.ai / chatglm.cn, which needs a credential. The shape of that call — FE-version and region headers, account rotation on USER_BLOCKED with guest fallback — is what D3-vin / GLM-ZAI-2API got furthest with; pingmike2 / zai2api is the shorter Go version to read first.
Partner token/session donation verified on arrival partner.html's form POSTs to the hub's /tokens endpoint (fingerprint + person + status, never the value). The hub now checks each donation against Aliyun as soon as it lands, so a status of valid or invalid comes from a real exchange and anything else settles as unverified rather than being claimed good. A minted param is what the chat path spends; donated values still stop at verified-and-recorded. Because each check is an outbound call, one caller may have 4 verifying at once (GLM_DONATE_CONCURRENCY); past that the hub answers 429 + retry-after and records nothing, so a flood is bounded rather than fanned out. Volume is not capacity: a thousand donated sessions buy no chat throughput.
Per-person identity revocable at runtime GLM_PEOPLE (name=role:key) gives each person their own key; their name rides on sessions, mint sockets and donations, and /people lists the directory to admins. A superadmin is seeded at startup from GLM_SUPERADMIN (or a generated key printed once), creates people with POST /people and sees the key once. An admin revokes or rotates from the People card below: the key dies on the next request, and the person's live sessions and open mint sockets are dropped with it. With GLM_STATE_FILE set the directory is a JSON file written on every change, so a revocation survives a restart, and the seeded superadmin lives there too - as a salt and a hash, never the key itself. A key pinned in the environment refuses both actions on purpose.
Real captcha mint unproven glm-client.js now takes the scene from the hub's /config (env-driven, captured defaults) and loads the real SDK whenever a hub answers; with no hub it runs the labelled demo. The hub can exchange a param with Aliyun, but no real verification parameter has been produced here yet.
Reference: chaoticmindv / zai2api is the one to read here — it triggers the widget by sending a message and waits for the token to appear, which is the same browser path this project uses. pingmike2 shows the opposite choice: the whole captcha solved in-process (build args → track hash → compress → encrypt → verify), which needs no browser at all but breaks when Aliyun changes the challenge.
Tor egress relay only A Tor SOCKS5 port is just another route: used round-robin, marked dead on a failed handshake, labelled tor in x-glm-egress. Nothing here speaks the Tor control protocol and nothing rotates a circuit, so the exit is only as fresh as the local daemon's choice — which needs a control-port client before it can be called circuit rotation.
Reference: none of the three has Tor, so there is nothing to copy. The nearest pattern is D3-vin's WAF proxy rotation with a 10-minute dead-proxy timeout — the same bookkeeping (mark a route dead, stop using it, retry elsewhere) applies to circuits, and its proxy.txt one-address-per-line format is a sane shape for a circuit list.
Token pool behaviour has a consumer Entries carry an expiry, the sweep moves expired ones out (counted, never dropped silently), and the hub refills towards low-water and target. The chat path now takes an entry and spends it: the oldest minted param is attached to the upstream call as captcha_verify_param, a 401/403/429 returns it unspent, and the response carries x-glm-pool: spent|empty. An empty pool still forwards, labelled, rather than refusing. One caller holds at most 4 chat requests at once (GLM_CHAT_CONCURRENCY); the next gets 429 with retry-after and spends nothing, then waits GLM_CHAT_COOLDOWN_MS (5s) before retrying.
Reference: pingmike2 / zai2api's queue discipline — ORDER BY id LIMIT 1, delete after use, refill below 50 — is the shape this now follows, minus SQLite: the hub's queue is memory.
Job scheduling server-side now The hub picks the partner asked longest ago, one job in flight each. The minter page's local demo pool still runs when no hub answers.
Admin authentication keyed + revocable Admin, partner and superadmin sessions need that role's key, compared in constant time; user is open on purpose. /status returns 401 without a session and 403 without an admin-level role. A person from GLM_PEOPLE can sign under their own name, and the seeded superadmin signs under its own. Every page also needs a session now: signed out, it redirects to login.html?next=…. Revocation and rotation are live: POST /people/revoke and POST /people/rotate take effect on the next request, and drop the person's sessions and sockets.
Job authorisation session required The /minter/ws upgrade now refuses a socket with no session, and the partner table shows which role opened it. GLM_WS_AUTH=open restores anonymous sockets, and the hub warns loudly when it does.
Two token sources catalogued The model catalog covers both: z.ai/… routes to chat.z.ai (its /api/v2 path, overseas region) and cn/… to chatglm.cn (its /api/v1 path). What is not yet exercised: a live call through each, which needs an upstream credential.
Persistence directory on disk With GLM_STATE_FILE set, the people directory - created people, their roles, a salt and a scrypt hash per person, the seeded superadmin, and revocations - is a JSON file written on every change (0600) and reloaded on start, so a revoked key stays revoked across a restart. No key is ever written: a copy of the file is a list of names, not a set of credentials, and a version: 1 file that still held plaintext keys is hashed and rewritten the first time the hub reads it. The pool, sessions and donation log stay in memory on purpose: pool entries are captcha params that expire in half an hour, so persisting them would be a liability rather than a feature.
Endpoints listed above forward when configured /v1/models answers with the full catalog. /v1/chat/completions resolves the model id, spends one pool entry, signs the request and forwards to GLM_UPSTREAM; without it, 501 with its reason. No credential ships with the project, so forwarding is opt-in — and the forwarded call itself is proven against a stub, not the real upstream.
Background-tab survival unverified The silent oscillator is in place, but whether real browsers keep it alive long-term has not been observed.
Visual confirmation unverified The look is matched from recorded design tokens and checked statically; no browser screenshot has been compared against the original.
Kept deliberately blunt: a gap that is written down is a gap someone can close, and a "done" that was never verified is worse than an honest blank.
In plain words — what "not done" means here. It does not mean the code is broken or half-written. It means one specific step has not been proven because it needs something this machine does not have:
  • No live upstream — nobody supplied a credential for chat.z.ai or chatglm.cn, so the hub can build the request and validate the model id, but it will not claim a reply it never got. Close it by setting GLM_UPSTREAM; the same code path then forwards for real.
  • No real captcha mint observed — minting happens in a partner's browser against Aliyun's widget, so it needs a browser with a screen on the live site. Nothing here can fake it, so the demo path is labelled a demo. Close it by opening the minter tab on a machine that can reach chat.z.ai.
  • Nothing spends a token — entries are donated, verified and expired, but the only thing that would spend one is a working upstream, which is the first gap. Close it by closing that one.
  • Egress routing — a hand-written SOCKS5 client tunnels the chat forward and the upstream-key probe through the routes in GLM_EGRESS_ROUTES, round-robin, and each chat response says which one carried it in x-glm-egress. Captcha verification and the donation exchange stay direct, because the widget breaks behind a proxy. Watch it by reading the egress panel: a route that fails a handshake is held dead for GLM_EGRESS_DEAD_MS.
Everything else on this page — keys, sessions, the page gate, the mint socket, the even spread, expiry and refill, donation verification, the model catalog — is exercised by npm run check against the real hub on every run.
